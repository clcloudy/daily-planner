# Daily Planner 长期维护方案

这份文档用于让不同时间、不同会话中的 agent 持续、安全地更新 `daily-planner`。

## 推荐工作循环

每次更新都按以下顺序执行：

1. **读取上下文**
   - 阅读 `AGENTS.md`、本文件、`package.json` 和相关模块。
   - 执行 `git status --short --branch`，识别用户已有修改。
2. **明确变更**
   - 将需求拆成一个可以验证的最小任务。
   - 记录影响范围：UI、数据模型、计时器、路线图或构建配置。
3. **实现**
   - 优先沿用现有组件、类型和本地存储结构。
   - 任何数据结构变更都提供默认值或兼容读取逻辑。
4. **验证**
   - 执行 `npm test` 和 `npm run build`。
   - 交互变化需要用本地开发服务器检查主要流程。
5. **提交**
   - 只暂存本次任务相关文件。
   - 使用清晰的 Conventional Commits 提交信息。
6. **同步**
   - 推送到 `origin/main`。
   - 最后用 `git status` 和 `git ls-remote --heads origin main` 确认本地、远端一致。
7. **交接**
   - 在最终报告中记录变更、测试、提交哈希、推送结果和遗留风险。

## 变更规模与分支策略

- 小型修复、文档更新和低风险 UI 调整可以直接在 `main` 上完成，但必须一次提交、一次推送。
- 中大型功能建议使用短生命周期分支，例如 `feature/habit-calendar` 或 `fix/timer-persistence`。
- 分支完成后先运行完整验证，再合并到 `main` 并推送。
- 不保留长期漂移的个人分支；合并后删除已完成分支。

## 功能演进顺序

建议按以下阶段逐步演进：

### 阶段一：稳定首版

- 保持习惯、待办、番茄钟和路线图的核心流程稳定。
- 增加关键数据层测试：本地日期、连续打卡、计时完成、旧数据读取。
- 为用户可见的破坏性变更加迁移逻辑和发布说明。

### 阶段二：可恢复性

- 增加本地数据导出和导入。
- 增加版本化的数据迁移函数，例如 `v1 -> v2`。
- 提供清晰的“恢复默认数据”入口，并在执行前二次确认。

### 阶段三：协作与同步

- 在引入账号前先定义服务端数据模型、冲突策略和隐私边界。
- 将 localStorage 抽象成可替换的数据接口，保持 UI 不直接依赖存储细节。
- 云同步上线前保留本地导出，提供失败重试和离线使用能力。

### 阶段四：自动化质量

- GitHub Actions 执行 `npm ci`、`npm test` 和 `npm run build`。
- 依赖升级使用独立提交，并在升级后检查安全审计结果。
- 每次发布创建版本标签和简短变更记录。

## Agent 的长期工作方式

- 每次新会话都从 `AGENTS.md` 和 Git 状态开始，不依赖历史记忆。
- 一个任务只解决一个主题，避免把无关重构混进功能提交。
- 修改前后都优先查看真实代码和测试结果，不根据猜测操作。
- 如果 GitHub 凭据失效、推送被拒绝或出现合并冲突，停止声称“已同步”，并把阻塞原因交给用户处理。
- 如果需求改变了本仓库的代理规则，先由用户明确要求，再单独提交 `AGENTS.md` 的修改。

## 建议的发布检查表

- [ ] `AGENTS.md` 已阅读，且未被无授权修改
- [ ] `git status` 中没有误纳入的用户文件
- [ ] `npm test` 通过
- [ ] `npm run build` 通过
- [ ] 受影响页面已手动检查
- [ ] 提交信息清晰
- [ ] 已推送 `origin/main`
- [ ] 远端分支哈希与本地 HEAD 一致
- [ ] 最终报告已记录测试、提交和推送结果
